## 第一步的数据与交互

- `planning.day_windows` 按本地日期保存每日起止时间；允许时间暂缺的草稿，排程时明确待补。活动约束增加日期分配。
- `planning.overnight_stays` 明确每一晚及已核对住宿候选，可复用用户指定地点。酒店不必加入游玩选择，候选存在也不代表每晚都住；缺一晚保持对应缺口及未知接驳。
- 当前接口提供可选酒店池供界面选择，冻结输入只签入实际引用酒店。住宿作为当日终点、次日起点；入住、退房、寄存、房态和当前房价无依据时保持未知。
- `PlanPayload.days` 按本地日期组织起终点、交通、活动、住宿关联和问题；保留平坦时间表以兼容既有历史、采用与比较。确定性编排复用 P4 市内核，不能简单删除单日/同城保护后跨城市套路线。

## 贯穿 P5 的约束

1. 整个 Run 共享高德、模型、搜索、时间和组合预算，不按天重置；外部请求、缓存命中、未知用量沿用现有账本。
2. 铁路用独立的铁路项目及用户确认来源，站点引用真实 POI、时刻带时区。高德市内交通不充当铁路班次，无可靠时刻时明确待确定，不编余票、票价或准点保证。
3. 不新增订房、购票或库存采集。住宿补查只提供来源及位置，历史消费不转成当前可订价格。
4. 保存方案保持不可变，显式采用继续校验行程、请求版本、实质输入及有效期；新输入不得借多日展示绕过历史/锁定保护。调整只影响相关日和下游，旧版保留。
5. API 集成使用临时库和外部 Mock；真实 Web/SDK/来源验证单独记录日期、范围、用量与失败。测试不默认请求真实账号，验收数据不写正式数据库。

第三步增加 `rail_segments`，只接收用户明确确认的车站、车次和带时区时刻；真实火车站候选与所选游玩独立，实际引用站点进入输入签名。铁路是独立时间表项目，高德只计算两端同城市内接驳；默认进站 30 分钟、出站 20 分钟是可修改的程序预留，不作为车站政策或准点承诺。修改班次/时刻会清除界面确认状态。无可靠班次保留待定草案，路线或额度未知记部分结果，已证实的赶车/预约/预算冲突阻止采用。
