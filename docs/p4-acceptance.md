# P4 单城单日规划：实施与验收

记录日期：2026-10-14 至 2026-10-15。按用户更正后的 P4 目标及落地方案 §8.4 分步交付；多日住宿与铁路不在本阶段。P2 语义质量和 P3 人工消歧认证的既有限制继续保留。

## 切片 1：规划输入与方案版本底座

- `TripRequest.planning` 保存用户的返程、步行上限、禁用交通、缓冲、必去/排除、活动时长、费用、时间窗和固定预约。时长与费用数值必须同时标记来源，空值保持未知；互相矛盾的约束被拒绝。日期带时区，Windows 通过 uv 锁定 `tzdata`。
- `GET /planning-input` 读取本行程已经选择并确认的真实 POI、活动和原来源快照。缺起点、日期、期限、选择或可确认城市时明确列出待补项。P3 来源不因仅修改出发时间或交通条件而被强制重新采集。
- 签名包含行程、实质规划条件、真实起点及选择快照，排除地图视野/页签和来源全局读取计数。起点或选择改变会使旧方案不可采用，缩放不会无故使方案失效。
- 连续迁移 `005_plans.sql` 增加不可变方案版本、采用记录与当前方案指针；旧数据库数据保留。旧方案仅供查看，不自动覆盖当前方案。方案保存仅供服务端调用，没有供客户端提交虚构路线或 `validated` 状态的接口。
- 时间表页可编辑并自动保存规划条件、显示缺输入和已选真实地点，区分用户确认、来源报告、程序估计与未知。读取失败保留本地编辑；切行程后旧响应不落入新工作区。

## 切片 2：真实路线与单日排程

- 通过既有任务执行器运行 `plan`，按冻结输入、路线排程、版本保存三个检查点恢复；取消、输入变更、未知请求和晚到响应均不能继续发布。生成不等于采用，原采用操作重试返回当前真实指针。
- 真实高德路线规范化为步行、公交、骑行、电动车或驾车段；使用真实城市编码，方向/模式/日期时段缓存，统一应用级 1.1 秒调用门。单轮最多 3 组与 40 次物理请求，城市查询也计入账本。公交总耗时含步行/等待，缓冲另外展示；几何不全不补直线，共享车辆只显示条件。
- 检查固定预约、时间窗、步行、费用、禁用交通和返程期限。未知活动时长不会继续编造下游时间，无法完成必去活动不会悄悄删除。起点城市从真实 POI 或用户确认读取。午晚餐缺口先保留，实际补查在下一切片。
- 前端显示真实时间表、路线、费用来源、未知和冲突；只有可采用且有效的版本可显式采用。方案比较、保存失败重试和切换行程保护继续沿用原工作区。

## 切片 3：餐饮补查与进度排程服务

- 餐次查询绑定真实排程窗口及附近 POI，最多 2 搜索、2 篇原文、总 5 条评论、4 模型请求、0 图片。复用 P2 只读工具、引用/活动校验、来源与模型账本；复用 P3 真实地点、同城/类别/分店核对。45 分钟补餐停留明确是程序估计，费用和忌口保持未知。
- 餐馆候选独立保存于 `supplements`，原选择和 hash 不被后台改写；按真实路线再次排入窗口。网络、未知结果、歧义、预算耗尽或不能排入时保留餐次缺口和已经取得的原路线。成功抽取与缓存读取均重新核算实际分析篇数、评论与证据，不重复请求或累计。
- 当前位置与时间由用户成对提供。原出发点仍是返程终点，总期限仍从原出发时间计算。服务保留无关前缀及完成/锁定快照，只计算受影响后缀；修改步行限制会重新选择适用交通。跳过再完成的历史可保存，未经确认的旧交通不计为实际步行或费用。
- 采用在服务端核对历史完整内容与当前采用父版本；不能删除完成事实、修改历史路线、改晚锁定预约或以未知共享车作为硬期限唯一依据。旧版过去的出发时间要求明确现在进度，跨日仅保留历史查看。
- 新迁移 007 保存原子替换回执，既有行程、地图与方案不丢失。替换保护完成/必去/锁定/预约、同城真实 POI、两个版本和语义 hash；相同 UUID 的历史确认返回当前状态，不回写后来的选择。
