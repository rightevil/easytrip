# EasyTrip 同类产品与当前故障研究

日期：2026-10-30。状态：研究结论与布局建议，待用户审阅；不代表已开发或已完成竞品实机测评。

## 研究范围与证据

沿用用户选定的快速路径。本轮围绕行程/地图布局、AI 对话与结果、开源实现三个方向进行六次 Exa 检索，返回 30 条结果；结果去重、筛选后，以官方产品页、帮助文档与项目仓库为依据。精读九个去重产品页面，另核对 MDN 的 429 说明。未登录竞品、未购买服务，未把官网宣传速度或准确性当成实测。

用户截图和本机桌面数据库仅用于当前故障与布局分析，未提交给搜索服务。没有重新发起真实模型、小红书或地图请求，没有操作桌面。尝试取用 Tripomatic 官方截图文件时发生读取超时；未将页面文案、图片 alt 或搜索摘要冒充视觉实测。

## 先处理截图里的实际故障

只读打开 `%LOCALAPPDATA%/EasyTrip/easytrip.sqlite3`，最新发现任务停在 understanding，状态 paused，停止原因为 model_request_failed。动作台账记录 HTTPStatusError、http_status=429，任务记录耗时约 0.719 秒；小红书搜索次数和取得笔记数均为零。

**可确认：模型 HTTP 请求返回 429，需求理解没有成功，小红书采集尚未开始。** 不能据此认定 exe 进程崩溃、图片读取失败或所有 API Key 无效。

[MDN 的 HTTP 429 说明](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Status/429)定义了请求速率受限的含义及可选 Retry-After。当前台账未保存上游细分原因和等待提示，无法进一步断言是账号额度、并发、共享服务流控中的哪一种；这需要脱敏错误分类或供应商侧记录，而不是盲目重放收费请求。

现有代码把 HTTP 错误归入请求失败/结果未知，页面再统一展示“模型调用中断，需新一轮继续”。这保留了未知计费，但损失了实际可用的状态码；用户只能面对泛化的中断提示。

### 建议的失败呈现与行为

- 429：显示“模型服务暂时限制请求，尚未完成需求理解”；给出设置入口、明确的重试操作与折叠详情。仅在上游提供有效 Retry-After 时显示真实等待提示，不编造倒计时。
- 凭证拒绝、权限错误、超时、网络失败、输出校验失败分别解释，不能全都叫模型中断。错误详情只保留经过过滤的状态码、分类和请求标识，不原样显示上游正文、密钥或私有 URL。
- 没有结果时不展示大块全零覆盖统计；显示简洁失败卡和继续填写/浏览已有内容的入口。已有候选或采用方案时，结果区域保持可用。
- 重试有次数、时间和预算边界；429 不等于永远等待就能成功。结果未知的收费请求继续保留未知状态，不默认为零消耗或静默重发。
- 本机格式检查与真实连接状态明确区分。发现任务的错误应能定位到设置中相应服务；不能把当前“配置齐全，未测试连接”包装成服务正常。

## 从截图得到的具体问题

1. 左侧行程导航与中间常驻条件表单共同占用宽度，候选内容被压缩；地图没有参与用户当前的选择过程。
2. 信息层级重复：候选地点标题、有来源标题、发现轮次、状态条后才是大量计量，真正结果处在下方。
3. 首次理解失败、尚无结果时，仍出现“已分析、沿用、图片提交”等多排零值，用户难以判断该处理什么。
4. 偏好与想法、正式目的区域和起点属于不同语义，应让用户看懂系统理解的目标，不能只保留长表单和一个默认行程名。
5. 一次完整发现、地点专项搜图、地图展示和行程编排的状态需要分别呈现，不能图片或模型一个步骤失败就令整页失去用途。

## 建议的页面组织（提案，尚未批准）

保留现有整体主题与桌面载体，本轮不擅自更改品牌色或引入新的 UI 框架。参考来源只支持交互模式；下面的具体布局是给 EasyTrip 的设计建议。

```text
窄行程导航 | 行程标题、保存状态、紧凑条件摘要、编辑条件
          | 找地点 / 看行程                任务状态详情
          |---------------------------------------------
          | 地点卡片或按天时间线       | 地图与选中地点
          | 参考图、匹配理由、取舍     | 同步定位/路线
          | 替换/收藏/加入行程        | 点开地点详情
          |---------------------------------------------
          | 告诉助手：换个安静的 / 不想走这么远……
```

- **条件编辑**：顶部显示目的区域、日期、可用时长、起点、人数、预算等摘要；详细字段放侧边编辑面板。未明确的条件显示待补充，不编造默认值；缺少排程必需条件不等于禁止浏览地点。
- **找地点**：卡片先展示专项检索打卡图、地点/区域、适合当前要求的理由、主要缺点；图片异步补齐，打开查看图库和来源。没有匹配图时保留可用卡片，不拿其他地点图片填充。
- **看行程**：同一区域切为按天时间线，交通和停留可见，右侧地图显示当前日路线；候选池仍能返回。用户不必再回条件页面逐个配置普通活动才能理解草案。
- **对话**：底部或可收起的上下文面板承接自然语言调整，不另占一个常驻完整宽栏；这属于待验证布局建议。
- **任务状态**：只占简洁状态卡；运行时说明正在做什么，有结果则先显示。统计、历史轮次和技术详情展开查看。
- **失败**：错误区域显示受影响步骤和适当操作；保留输入和已有结果。理解失败时不要出现可误认成正式推荐的虚构占位地点。
- **窗口较窄**：地图/列表切换，避免强制三栏；大字号、高系统缩放和键盘访问需进入后续验收，不凭截图宣称已适配。

## 与用户已确认搜图规则的对应

仍按“确定具体地点 → 地点名＋城市/分店线索专项搜索打卡笔记 → 筛选匹配图片 → 卡片/图库展示”设计。以上竞品都不证明已有小红书专用搜图能力；这是 EasyTrip 需要单独实现和验证的流程。图片归属、来源追溯、缓存、用量、取消和恢复需形成同一契约，不能只换一套卡片样式。

## 建议顺序与退出条件

1. **先让失败可处理**：提炼 429 等错误、保留状态码与可用等待提示；用户在首屏能知道失败原因、已有内容及下一步；不能承诺修复供应商侧限制。
2. **确定结果工作区**：用同一布局覆盖空白、运行中、部分结果、失败有结果、失败无结果和采用方案六类状态。条件编辑与结果宽度不互相挤压。
3. **接入地点图片流程**：独立搜索、可追溯图库、按需加载与失败降级，图像关联错误有调整入口。
4. **检验结果与恢复质量**：用用户实际的约会/周边游任务和受控失败案例对照，检查地点合适、路线可行与不重复处理；另验证 exe 中的可见错误与窗口缩放。

以上是未来设计/实现的验收方向，本轮未执行这些新增测试。已有 1217/172 项历史测试不能作为本轮真实模型服务可用性的证明。当前无产品代码改动、无重新打包，也未声称独立评审通过。
